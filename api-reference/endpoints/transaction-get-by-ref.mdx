## Overview

Retrieve detailed information about a specific transaction using either the transaction reference number (provided by Waypay) or your merchant order reference (the orderRef you provided when creating the transaction).

## Path Parameters

<ParamField path="reference" type="string" required>
  Transaction reference number OR your merchant order reference
  
  You can provide either:
  - **Transaction Reference** - The `txnRef` returned by Waypay (e.g., `WP20251212123456`)
  - **Merchant Order Reference** - Your `orderRef` provided when creating the transaction (e.g., `ORD123456`)
</ParamField>

<ParamField path="version" type="string" required>
  API version (e.g., "1")
</ParamField>

## Query by Transaction Reference vs Order Reference

This endpoint supports querying transactions using two types of references:

### Transaction Reference (txnRef)
- **What it is:** A unique reference generated by Waypay when a transaction is created
- **Format:** `TXN20251212123456` (system-generated)
- **Where to get it:** Returned in webhook notifications and API responses
- **Use case:** Query transactions when you have the Waypay transaction reference from webhooks

### Merchant Order Reference (orderRef)
- **What it is:** Your own order reference that you provided when creating the transaction
- **Format:** Your custom format (e.g., `ORD123456`, `ORDER-2025-001`)
- **Where to get it:** From your own system/database
- **Use case:** Query transactions using your internal order tracking system

<Note>
  **Recommended Approach:** Use your merchant order reference (orderRef) for easier integration with your system. This allows you to query transactions without storing Waypay's transaction reference.
</Note>

## Response Fields Explained

### Transaction Types (txType)
The `txType` field indicates what type of transaction this is:

| Value | Type | Description |
|-------|------|-------------|
| 0 | Payment | Customer payment/deposit |
| 1 | Refund | Money returned to customer |
| 2 | Payout | Withdrawal/disbursement |
| 3 | Settlement | Merchant payout |
| 4 | Fee | Transaction fee |
| 5 | Adjustment | Balance adjustment |
| 6 | Chargeback | Disputed transaction reversal |
| 7 | Reversal | Transaction reversal |
| 8 | Transfer | Internal transfer |

### Transaction Status (status)
The `status` field shows the current state of the transaction:

| Value | Status | Description |
|-------|--------|-------------|
| 1 | Pending | Transaction initiated, awaiting completion |
| 2 | Processing | Currently being processed |
| 3 | Success | Transaction completed successfully |
| 4 | Failed | Transaction failed |
| 5 | Cancelled | Transaction cancelled by user or system |
| 6 | Expired | Transaction expired (timeout) |
| 7 | Refunded | Fully refunded |
| 8 | PartiallyRefunded | Partially refunded |
| 9 | Disputed | Under dispute/chargeback |
| 10 | OnHold | Temporarily on hold |
| 11 | RequiresAction | Requires additional action |
| 12 | Declined | Payment declined |

## Best Practices

- **Use Order Reference**: Query by your `orderRef` for easier integration - no need to store Waypay's txnRef
- **Poll Wisely**: Don't poll too frequently. Use webhooks for real-time updates instead
- **Handle 404s**: A 404 response means the transaction doesn't exist or you don't have access to it
- **Store Transaction IDs**: Save the `id` field from responses for your records
- **Check Status**: Always verify the `status` field before processing the transaction
- **Fee Transparency**: Use `feeCalculationBreakdown` to understand fee calculations
- **Reconciliation**: Use `merchantOrderRef` to match transactions with your orders
- **Live vs Test**: Check `isLive` to distinguish between production and test transactions

## Common Error Scenarios

| Error | Cause | Solution |
|-------|-------|----------|
| 404 Not Found | Reference doesn't exist or access denied | Verify the reference is correct and belongs to your merchant account |
| 400 Bad Request | Invalid reference format | Ensure the reference string is properly formatted |
| 401 Unauthorized | Invalid or missing API key | Check your API key is correct and has not expired |

## Security Considerations

- Keep API keys secure and never expose them in client-side code
- Use HTTPS for all API communications
- Implement proper error handling for failed queries
- Log all transaction queries for audit purposes
- Rate limit your queries to avoid overwhelming the API
- Validate transaction data before using it in your system
